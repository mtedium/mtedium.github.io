Gitea Actions 怎么手动触发：从 workflow_dispatch 到没有按钮的排查

发表于2026-08-15|更新于2026-10-15|问题记录
|浏览量:

推送触发的构建已经有了，我又想保留一个入口：需要部署时，自己去网页点一下，而不是为了启动任务再改一次 README。

给工作流加上 workflow_dispatch 后没有看到按钮，我一度怀疑 Gitea 根本不支持。实际上，要分清三件事：服务器支持什么事件、页面识别了哪份工作流、Runner 能否接到生成的任务。

Gitea 支持手动触发，但要核对服务端版本

Gitea 在 1.23 发布说明中加入了 workflow_dispatch，支持通过 UI 携带参数手动运行。本文讨论的是素材中的 Gitea 1.26 场景；不能拿更早版本的经验直接判断，也不要把 Runner 的 3.x 版本当成 Gitea 服务端版本。

按钮由 Gitea 页面提供。Runner 负责执行任务；Runner 离线通常影响任务能否开始，不能直接证明手动触发能力不存在。

没有按钮，先确认看到的是哪份文件

排查顺序可以从这些具体信息入手：

  1. 工作流是否真的提交到远程仓库，路径是不是 .gitea/workflows/*.yml 或 *.yaml。
  2. 仓库是否开启 Actions，工作流有没有被禁用，当前账号有没有操作权限。
  3. 是否在 Actions 页选中了对应工作流，而不是只看所有运行记录的总览。
  4. 页面使用的分支和期望运行的分支上，是否都有正确的工作流定义，是否声明了 workflow_dispatch。
  5. Gitea 日志和页面是否提示 YAML、事件或参数解析错误。

为了减少分支发现行为带来的干扰，可以先把最小示例放到仓库默认分支，并在那个分支上验证。不要把 GitHub 对默认分支的全部规则未经核对地套给 Gitea；具体版本应以自己的页面和 API 为准。

“有一次提交没触发”也需要独立检查：提交是否推送到了监听分支、事件是不是 push、是否存在过滤规则或跳过标记。手动事件的存在，不会让本来不匹配的 push 自动匹配。

用官方 API 区分页面问题和触发问题

Gitea 1.26 的 工作流 dispatch API提供了独立验证入口。下面仅为调用示例，实际执行会创建一次运行；要替换域名、仓库和工作流标识，并在本地准备有相应仓库权限的访问令牌。

GITEA_API_TOKEN 是本地环境变量，不是示例中需要公开的字符串。工作流标识的具体接受形式，以实例自身的 API 文档和工作流列表返回值为准。

成功受理通常返回 204 No Content；没有响应正文不等于失败。400、403、404、422 则应结合响应说明检查参数、权限、路径和工作流状态。任务创建后还要看 Actions 运行记录，API 受理成功不等于构建与部署成功。

确认点下去执行的是哪一版

手动运行时要明确所选分支或引用，进入日志确认实际 commit。工作流里如果把 checkout 的 ref 写死成某个分支，可能与界面选择不一致。

同样，重新运行旧任务与发起一个新的 workflow_dispatch 是两种入口，不应假定它们一定选择当前最新提交。保留提交 ID，能让“这次到底部署了什么”有据可查。

手动触发只负责把明确的运行请求送进流水线。先验证入口和引用，再连接已有部署步骤，比为了触发一次任务制造空提交更容易维护。
