服务器有代理，Gitea Runner 为什么还是连不上？

发表于2026-08-15|更新于2026-10-15|问题记录
|浏览量:

服务器上的代理已经能访问外网，Gitea Actions 却在准备 actions/checkout@v4 时失败。给 Runner 加上代理之后，外网问题还没完全确认，Runner 访问自己的 Gitea 又变成了 502 Bad Gateway。

这两种错误看起来矛盾，实际暴露的是同一件事：代理运行在哪里、谁在发请求、这个请求该不该走代理，没有被分别说明。

这里的环境是 Linux 主机上运行代理核心，Gitea 与 Runner 通过 Docker Compose 部署；不是让服务器借用笔记本代理。虚拟局域网只是远程管理服务器的通道，不应该因为 CI 出错就跟着改它。

规则模式也需要流量先进入代理

代理的“规则模式”解决的是：收到请求后，选择直连还是某个节点。它不表示服务器上的所有应用、所有容器都自动把请求交给代理。

除非另行配置并验证了透明代理或 TUN 路由，否则 Shell、Runner 和 Docker daemon 都要有各自明确的代理入口。终端里的快捷命令可能只是导出环境变量，不会自动影响已启动的容器。

服务器上没有桌面客户端也可以运行代理核心。脚本安装器、核心程序和管理面板是不同组件；核心负责转发，面板负责管理，yq 这类工具只负责处理配置。不能把某个 GitHub 项目名字直接当成 Homebrew formula，更不应凭 star 数量判断它能否适配当前环境。

以 Mihomo 为例，配置中的 HTTP、SOCKS 和 mixed 监听端口与外部控制接口用途不同。管理面板能连接 9090，不等于 9090 就能用作 HTTP 代理。

直接运行 curl -I 不能保证是在直连，因为它可能读取已有代理环境变量。两条命令明确表达路径，才方便比较。

若先出现 200 Connection established，它表示 HTTP CONNECT 隧道建立；还要看后续 TLS、目标站点响应与命令退出状态。一次请求成功，也只证明这个进程到这个目标的路径可用。curl 的代理选项文档说明了显式代理和绕过规则。

第二层：容器里的 localhost 指向自己

Runner 容器里的 127.0.0.1 指向 Runner 容器，不能直接访问只监听在宿主机 loopback 上的代理。

为什么加代理以后访问 Gitea 会报 502

Runner 需要访问内网的 http://server:3000。如果它也把这个请求交给 HTTP 代理，代理可能既不认识 Docker 服务名 server，也不在同一个网络，于是返回 502。

这只是与现象相符的假设，仍需验证。可在具备 curl 的 Runner 环境中，对同一地址比较继承代理和强制直连的响应，再看代理日志与 Gitea 日志：

直连成功、经代理失败，才支持把问题收敛到代理路径。NO_PROXY 中应列出实际请求使用的主机名，例如 server；只列 IP 段不能保证所有客户端都会先解析再匹配，CIDR 的支持也不完全一致。

NO_PROXY 的含义是“这些目标不经代理”，不是“禁止访问这些目标”。Gitea 本来就在同一个 Docker 网络时，保留 server 往往正是需要的配置。Runner 的代理说明要求为需要直连的 Gitea 实例明确加入排除项。

第三层：daemon 拉镜像要单独配置

日志里还有这条警告：

它说的是镜像拉取路径，不是当前 502 的直接证明。Runner 有代理而 daemon 没有时，获取 Action 代码和拉取 Job 镜像可以呈现不同结果。daemon 的配置方式见 Docker 官方代理文档。

Runner、任务容器与 daemon 在同一台服务器上，也仍是不同的进程环境。Runner 3.x 会把常用代理变量提供给 Job，但 Job 是否能解析代理地址、是否能到达那个监听入口，仍要单独确认；给 Runner 增加的 hosts 条目不自动变成 Job 的 hosts。

按下载阶段判断下一步

失败位置 实际关注的对象
docker pull / Job 镜像准备 Docker daemon 到 registry
Prepare all required actions Runner 获取 Action 仓库的链路
Checkout 的 git fetch Job 到业务仓库
npm ci Job 到依赖 registry

actions/checkout@v4 首先需要获取 Action 自己的实现，再由它拉业务仓库。Gitea 默认从 GitHub 获取省略主机名的 Action；自建 Gitea 不会自动带齐所有第三方 Action。官方 FAQ解释了来源和绝对 URL 的用法。

如果改为内网镜像仓库，应先实际同步对应 Action 和所需版本，再引用它。把 URL 换成一个不存在的仓库，只会把连接失败换成 404。

验证的是链路，不是“服务器装过代理”

应用修改后执行 docker compose config --quiet、docker compose up -d runner，再看新一轮日志。不要因 502 就删除注册状态，也不要看到后续任务能跑，就以为镜像、仓库和依赖下载全都验证完成。

对这类问题，我现在会先写下“谁访问谁、应不应该经代理、入口在哪里”。这三个问题明确以后，规则模式、容器网络和内网直连才不会搅在一起。
