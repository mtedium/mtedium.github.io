Runner 能找到 Gitea，为什么 checkout 却解析不了 server？

发表于2026-08-15|更新于2026-10-15|问题记录
|浏览量:

Runner 已经在线，日志也显示领取了任务，流水线却在 checkout 时报：

最让人困惑的是：Gitea 和 Runner 明明在同一个 Compose 网络里，Runner 也一直用 http://server:3000 通信。为什么一执行任务，这个名字突然不存在了？

关键是换了执行环境。

同一个服务器不代表同一个网络

这次采用的是容器化 Runner，通过宿主机 Docker socket 创建 Job 容器。要区分三个对象：Gitea 容器、Runner 容器和临时 Job 容器。

Compose 把前两个服务接进同一个网络，并不会自动约束 Runner 之后通过 Docker API 创建的每个容器。Job 可能加入 Runner 新建的任务网络，那个网络里没有 server 这个服务名。

位置 能否解析 server 能证明什么
宿主机 Shell 取决于主机 DNS 与 hosts 只说明宿主机的解析环境
Runner 容器 同网时通常可以 领取和汇报任务可能正常
Job 容器 取决于任务网络 checkout 真正需要在这里成功

Docker 服务名的解析属于 Docker 网络提供的能力，不能把 Runner 里的测试结果直接推广到任务容器。Compose 网络说明解释了同网服务名和宿主机发布端口的区别。

先看错误发生在哪一步

Could not resolve host 发生在建立到目标的连接之前；认证失败通常会出现 HTTP 401、403 或 Git 权限提示。此时贸然添加个人 Token，无法修复 DNS。

同样，connection refused 表示已经尝试连接某个地址，502 表示某个网关返回错误，它们和名称解析失败需要不同证据。Runner 日志先短暂拒绝连接、之后显示 declare successfully，应结合时间判断服务是否已经恢复，不能只盯着旧的一行。

配置文件里不能混入命令输出

整理这次问题时，还遇到了两种配置错误：旧命令名 act_runner 在新的 gitea/runner 镜像中不存在；生成配置的弃用提示被粘进了 YAML 第一行，导致反序列化失败。

Runner 3.x 使用 gitea-runner，具体子命令先看同版本的 --help。若当前版本提示 generate-config 已弃用，就按其帮助改用 config generate。不要把终端的错误、提示或 Nano 状态栏复制进配置文件，也不要用 2>&1 把 stderr 合并到 YAML。

最小配置只保留需要覆盖的字段即可，但已有自定义配置要合并，不能直接覆盖丢掉标签、缓存或挂载限制。

方案二：使用各执行环境都能访问的实例入口

如果 Runner 将来要跨主机扩展，稳定域名或固定内网入口更容易维护。不过要分别确认浏览器、Runner 和 Job 都能到达它，并处理证书与代理排除规则。

假设宿主机映射为 3010:3000：

  • 在共享 Docker 网络里，可以访问 http://server:3000。
  • 经宿主机内网地址访问时，应使用 http://git.internal.example:3010。

把 server 映射到 host-gateway 后还继续访问 :3000，不一定能到达发布在 3010 的入口。名称解决了，不代表端口也对了。

Gitea 的 ROOT_URL 应表达客户端实际使用的公共入口。不要为了临时方便就把仅容器内可解析的 http://server:3000/ 宣传成所有人的克隆地址。Gitea 服务端配置说明给出了 ROOT_URL 的含义。

代理排除和 DNS 是两项检查

NO_PROXY=server 能让内部访问避开代理，但不会创造 server 的 DNS 记录；把 server 从 NO_PROXY 删除，也可能只是让解析问题转移给代理，再变成 502。

共享网络要解决服务发现，代理排除要决定流量走向。两项都正确，内网 checkout 才有稳定路径。

修好以后怎么证明

Runner 在启动时读取配置。只修改已经挂载的 config.yaml 时，普通 up -d 可能不重建容器，也就不会重读文件；修改 Compose 定义与修改挂载文件内容，需要分别处理。先确认没有正在执行的任务，再校验 Compose 并重建 Runner，保留 /data 注册状态，最后检查新任务的网络：

这里最后一个名称按实际设置替换。验证标准是任务运行期间能看到 Job 加入目标网络，checkout 的真实 git fetch 成功，后续步骤开始执行。Runner 在线只是其中一段证据。

一旦把 Runner 和 Job 分开看，“同网了为什么还找不到”的矛盾就消失了。真正要检查的是发生报错的那个容器，而不是挑一个方便进入的容器代替它。
