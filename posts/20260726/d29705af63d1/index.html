明明已经删掉的代码，为什么 merge 后还在？

发表于2026-07-27|更新于2026-10-15|问题记录
|浏览量:

这次排查原本只是清理一个没有调用方的兼容别名，却把我带到了一个一直没有想清楚的问题上：

公共分支早就删掉这段代码了，为什么我把公共分支合进来，它还留在自己的分支里？Git 不应该记得那次删除吗？

直觉上，我把合并理解成“把对方最近做过的操作再执行一遍”。但对这次问题，真正有解释力的是三个位置的文件快照：共同祖先、当前分支和对方分支。

起点：一个不再需要的别名

原始问题中，有一段为了旧命名保留的导出，下面把名称简化：

公共分支已经做过命名统一，并删除这个别名。我自己的分支上，它却仍然存在。

第一轮排查，我用 git blame 找定义的来源，又用 git log -S 查相关文字的增减，以为抓住了问题。但这些命令解决的是特定角度的问题：某行最后由哪个提交形成，哪些提交改变了某段文字的出现次数。它们不能代替合并拓扑和实际文件内容。

尤其是默认的路径历史展示、merge diff 形式，都可能省略排查时真正关心的那一面。看到几条提交，不等于已经把两条开发路径的状态对照完整。

真相藏在共同祖先里

沿着两条分支查下去，关键事实是：公共分支的那次删除，已经进入了双方的共同祖先；我的功能提交后来又把别名加回来了。

把具体提交 ID 去掉，只保留关系，可以表示成：

对应的三方状态是：

位置 别名是否存在 相对 base 的变化
base 不存在 比较起点

theirs，公共分支 不存在 无变化

从我的视角看，它像“公共分支删了，我这里没删”。从这次合并的比较起点看，它却是“公共分支没有改，我这里新增”。对这样一个可独立合并的新增，Git 通常会保留它，也就没有理由报冲突。

如果对方 tip 恰好就是 merge base，说明对方已经是当前分支的祖先，重复 merge 还可能直接返回 Already up to date。这种情况下，更不会再执行一遍旧的删除。

删除不会成为永久规则

对常规三方合并，可以先按下面的方式判断某个独立区域：

base ours theirs 通常的合并结果
A A B B
A B A B
A B B B
A B C 同一区域不兼容时可能冲突

实际文件还可能涉及重命名、文件删除、上下文变化等情况，这张表只是理解三方比较的起点。

Git 保存历史，却不会把历史上的“删掉别名”解释成“今后禁止重新引入这个符号”。如果两边的最终状态足以得到合并结果，它不会逐条重放中间的命令。这一点也写在 git-merge 官方文档中：三方合并主要考虑双方 tip 和 merge base，而不是逐个考虑中间提交。

反过来说，如果 base 中有一个文件，一边删除，另一边修改，可能得到的是 modify/delete 冲突。不能把“删除会被自动保留”或“删除一定会赢”概括成通用规则，先看 base 才有意义。

-S 适合追踪字符串出现次数的变化，但不是万能的语义搜索；git show -m 则把合并提交分别与各父提交比较。只看默认合并展示中没有某段 diff，不能证明它在所有比较方向上都没有变化。关于逐父提交的展示，见 git-show 文档。

没有冲突，也要检查最终行为

这次真正需要决定的，并不只有“留下别名还是删掉别名”。同一个工具文件里，返回值约定、登录状态清理等行为也可能各自来自不同功能。

因此，处理时应该按意图逐项确认：别名是否仍有调用方；调用方需要空字符串还是 null；清理哪些状态是否与当前功能一致。不能为了“看起来与公共分支一致”而整文件覆盖，也不能因为 Git 没报错就认为业务含义一致。

需要在提交前查看合并结果时，可以在工作区干净的前提下使用：

确认后再提交，或者在仍处于合并过程时执行 git merge --abort。这里同时写 --no-ff，是因为只有 --no-commit 无法阻止快进更新；如果本来就已经合入，则不会凭空进入一次待完成的合并。具体行为见 merge 的 no-commit 选项。

分支策略可以缩小这种问题的发生范围

和同事讨论后，我更愿意把任务放在短期 feature 分支上：从当前集成分支创建，开发期间按团队约定同步，完成后通过 MR 合入，再结束这条分支的生命周期。

这样做可以减少长期个人分支反复吸收公共分支、又长期保留旧差异的情况。但它不会从机制上消灭语义冲突；rebase 同样需要验证，代码审查和有针对性的测试仍然要看合并后的行为。

删除功能分支也要区分合入方式。普通 merge 通常能从主线追溯原提交，squash merge 保存的是新的合并结果，不能笼统地说“删掉名字以后，每个原提交永远都在主线上”。

这次最有用的收获，是把问题从“Git 为什么不记得删除”改成了“这次合并相对哪个状态比较”。一旦把 base、ours、theirs 放在同一张表里，那段看似复活的代码，就有了明确来源。
