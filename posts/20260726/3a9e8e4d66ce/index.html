Git 的分支只是指针：从 reset 理解提交图

发表于2026-07-27|更新于2026-10-15|问题记录
|浏览量:

我对 Git 的理解，最早卡在一个看起来很简单的问题上：

有 a、b、c 三次提交，现在停在 c。执行 git reset HEAD^，撤销的是 b 还是 c？c 不是基于 b 做出来的吗？

如果只是背“撤销上一次提交”，碰到 revert、rebase 很快又会乱。真正让我把这些命令串起来的，是另一个发现：分支只是指向提交的引用，提交自己记录了父提交。

先把图上的线看明白

下面的图按时间从左往右画，线表示父子关系：

实际提交对象里的引用方向是从子提交指向父提交：c 记录 b，b 记录 a。main 指向最新提交 c，正常处于分支上时，HEAD 则指向 main。

所以 HEAD^ 表示当前提交的第一父提交，在这个例子里就是 b。它只是一个提交表达式；究竟会发生什么，要看哪个命令使用它。

reset 的参数是移动到哪里

在当前分支上执行：

会把 main 从 c 移到 b：

b 仍然在当前分支的历史里，c 不再能从 main 沿父提交找到。因此，描述为“让当前分支退回 b”比“删除 c”更准确：c 对象未必消失，其他分支、标签或 reflog 仍可能保留它。

更关键的是，默认 reset 不会把工作区文件直接恢复成 b 的内容。 对不带路径的提交级 reset，有三种常见模式：

命令 当前分支指向 暂存区 工作区
git reset --soft HEAD^ b 保持原样 保持原样
git reset --mixed HEAD^ b 恢复为 b 的快照 保持原样
git reset --hard HEAD^ b 恢复为 b 的快照 恢复为 b 的快照

没有指定模式时，默认是 --mixed。如果原先工作区干净，执行默认 reset 后，c 相对 b 的修改通常会变成未暂存修改，仍然在文件里。只有把分支、暂存区和工作区分开看，才不会把“提交退回了”和“代码没了”混在一起。见 git-reset 官方文档。

--hard 会丢弃受影响的未提交修改，还可能覆盖挡住写入的未跟踪路径。它不能作为理解不清时的试探命令。

目标仍然是 b，但这次 Git 会尝试在当前状态上抵消 b 相对父提交引入的变化，成功后新增提交 d：

所以这两个命令虽然都写了 HEAD^，含义却不同：

  • reset：把分支移到这个提交。
  • revert：在当前内容上抵消这个提交的变化。

revert 保留已有历史，但不保证后续功能不受影响。假设 b 把一行从 x = 1 改成 x = 2，c 又把它改成 x = 3，撤销 b 就可能发生冲突。即使不同行能自动合并，c 也可能依赖 b 引入的行为，最终仍需要验证。见 git-revert 官方文档。

对普通单父提交 b，可以用三方比较理解这次撤销：把 b 的快照作为比较基点，当前 HEAD 是一侧，b 的父提交 a 是另一侧，于是得到“从 b 回到 a”的变化。不能把 a 同时当成基点和另一侧，否则解释不出这个反向变化。

普通提交的输出会包含树对象、父提交、作者、提交者和提交说明。这里的树对象描述该提交对应的文件树；文件内容由 blob 等对象承载。Git 的逻辑模型是快照，底层存储可以再做压缩和增量优化，不意味着每次都原样复制整套文件。见 Git 对象。

通常一个普通提交有一个父提交；根提交没有父提交；合并提交可以有多个父提交。于是整段历史形成的是有向无环图，也就是 DAG：

m 记录了它的父提交。由它往回走，可以找到两条开发路径。线性历史只是 DAG 的一种简单情况，不能把 Git 的历史整体当成单链表。

分支不会写进每个提交的归属字段

我原先以为：某次提交在 feature 上产生，它就永远“属于 feature”。实际上，提交对象并没有这种排他的分支归属。

从 feature 可以沿父关系找到 e、d、b、a；从 main 可以找到 c、b、a。b 同时被两条分支的历史包含，并不需要复制。

创建分支，就是增加一个指向现有提交的名字；提交成功后，当前分支再向新提交移动。这就是 Git 分支轻量的原因。引用的具体存储可能使用独立文件、打包引用或其他后端，不应把“分支一定是某个目录下的文本文件”当成使用前提。见 Git 引用。

这里的 d′、e′ 是重新应用改动后形成的新提交，父关系等内容发生变化，因此对象 ID 也变化了。Git 并没有就地修改旧提交中的 parent 字段。实际过程中还可能跳过已存在或变空的提交，遇到冲突则需要处理。见 git-rebase 官方文档。

它让历史呈现方式发生变化，但不会理解业务，也不能自动避免语义冲突。共享分支是否允许改写历史，要遵循团队约定。

删除分支与删除历史是两件事

删除分支删除的是这个引用名。提交能否继续找到，取决于它是否仍被其他引用及相关保留机制覆盖。

如果 feature 通过普通 merge 合入 main，原提交通常可以从 main 追溯；如果采用 squash merge，main 保存的是合并后的新提交，并不意味着原 feature 的每个提交都已成为 main 的祖先。

误移动引用后，可以先查看本地 reflog，找到确认要保留的提交，再建立救援分支：

reflog 记录本地引用移动，存在过期策略，也不是覆盖所有对象的永久备份。不能把“90 天内一定能找回来”当成保证；尚未进入对象库的工作区内容也不会因为 reflog 自动恢复。见 git-reflog 官方文档。

我现在遇到 Git 问题，会先问三件事：当前引用指向谁，目标命令改的是哪个状态，相关提交在图上是什么关系。弄清这几件事以后，命令不再只是互相矛盾的口诀，死去的数据结构也终于能派上用场了。
