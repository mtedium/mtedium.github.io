React 项目目录怎么分？先让文件有明确归属

发表于2026-08-11|更新于2026-10-15|问题记录
|浏览量:

整理 React 项目时，我先列了一棵熟悉的目录树：components、pages、utils、store、assets。看起来很齐全，但真正写代码时，问题仍然会出现：页面里的 Header 算不算公共组件？一段业务计算是不是都该扔进 utils？新项目是不是要先建一整套空目录？

后来我觉得，目录规范要解决的核心问题很朴素：拿到一个文件，能判断它该放在哪里；修改一个功能，能找到与它相关的内容。

下面是一套适合普通 React 单页应用的起点，是项目约定，不是 React 官方规定。

先从一棵够用的树开始

这棵树按 Vite 风格的入口举例。main.tsx 负责启动应用，App.tsx 组织应用根部内容，router 只有在项目需要单独维护路由时才建立。采用其他框架或脚手架时，入口和路由位置应该服从它们的约定。

不用为了让目录“完整”而先创建 store、hooks、services、types。代码出现了，再为它确定位置。

public 和 assets 的边界由工具链决定

两者都能放图片，但使用方式不同。以 Vite 为例：

  • public 适合需要保留原文件名、直接按路径访问的资源，例如 robots.txt。
  • src/assets 适合由源码导入、参与构建处理的资源。

Vite 中，public/favicon.ico 在默认根路径部署下对应 /favicon.ico，而不是 /public/favicon.ico。通过导入使用的资源则参与构建资源图，生产文件名可能带哈希，小文件也可能内联。部署到子路径时，还要核对配置的 base 与资源引用方式。见 Vite 静态资源处理。

这也是为什么不能把某个旧脚手架里的 public/index.html 原样当成所有 React 项目的目录标准。在 Vite 的默认结构里，index.html 位于项目根部。见 Vite 项目根目录与 index.html。

页面私有组件先留在页面里

一个只供首页使用的 Header，先放在：

不要因为它名字通用，就提前放进全局 components。组件能不能复用，主要看它的职责和依赖：是否依赖当前页面的数据结构、路由参数或业务交互，而不是看它是不是一段 JSX。

等到多个地方确实需要同一种行为，再判断是否提取。比如应用导航框架可以放进 components/layout，而订单详情的业务摘要即使被几个订单页面使用，也更适合留在订单领域内部。

我的基本约定是：页面可以使用公共组件，公共组件不反过来导入具体页面。这样打开公共组件时，不会沿着依赖关系重新走回某个业务页面。

把组件拆到不同文件，是为了让职责清楚。React 本身支持通过普通 JavaScript 的导入、导出组织组件，并没有要求统一使用 pages 或 components 目录。见 React 组件导入与导出。

utils 不应该成为所有逻辑的终点

格式化日期、处理通用字符串这类纯函数，放在 utils 很自然。但下面这些内容不适合只因为“它是个函数”就放进去：

  • 订单状态流转规则，属于订单业务。
  • 登录状态与凭证处理，属于认证逻辑。
  • 调用后端接口，应该放在明确的请求或业务模块里。
  • 依赖 React 生命周期的复用逻辑，才考虑自定义 Hook。

例如某个页面独有的筛选逻辑，可以先和页面放在一起。以后真的跨页面使用，再移动也来得及。过早搬进全局目录，只会让“通用”变成没有边界的意思。

constants、types 也一样：通用配置可以集中，业务专属常量和类型尽量靠近业务代码。某个类型只被一个组件使用，通常没有必要先给它建全局出口。

状态放在哪里，先看谁拥有它

有了 store 目录，很容易顺手把页面交互都往里面放。但目录不应该反过来决定状态的生命周期。

输入框值、弹窗开关等局部交互，先交给需要它的组件。多个组件需要共享时，再放到它们合适的共同拥有者；跨路由长期共享且确有需要时，再考虑项目选择的状态方案。

服务端数据还涉及缓存、失效和重新获取，不能只把它理解成“再往全局 store 里放一份”。具体采用哪种方式，应与项目现有的数据获取方案保持一致。

功能变大，再按业务聚合

项目小时，按文件类型分类足够直观。业务扩大以后，如果修改一个订单功能总要同时翻 pages、hooks、api、types，就可以把订单相关内容聚到一个模块里：

这时页面负责路由入口和组合，业务模块承载订单自己的行为。只有项目真的出现这种查找和协作成本时，我才会引入这一层；小页面不必为了套结构再包一层空壳。

文件名也应服务于查找。Header.tsx、formatDate.ts 比到处都是 index.tsx 更容易区分；如果项目已有统一的 目录/index.tsx 习惯，保持一致通常比全量重命名更有价值。是否需要导出入口，则看是否存在稳定的模块边界。

对我来说，一份能执行的目录规范，只要先说清三件事就很有用：页面私有内容放在哪里，公共内容如何判定，业务逻辑由谁拥有。目录可以随着项目生长，归属规则应该先清楚。
