URL永远不会改,那还要不要把请求封装成 API 层?

一次关于「拦截器够了 vs 还要封装」的真实争论,以及我为什么一开始被问住了。

起因:请求根本没走 axios

翻一个 Vue 3 的 H5 项目,发现一件挺离谱的事:页面里调接口,大多数根本不走 axios,而是直接用浏览器原生的 fetch。

于是每一次要调接口,都得手写一遍请求头、手写一遍请求方法,错误码处理也各写各的、完全不统一。可 package.json 里明明装了 axios,前一任维护的人也认认真真写好了全局的请求拦截器和响应拦截器 —— 结果一个都没接上,全项目形同虚设。

粗扫一遍代码,现状大概是这样:

  • 页面/组件里直接 import request 的有 12 处,请求逻辑全糊在 UI 层;
  • 绕过所有拦截器、直接用原生 fetch 的有 14 处;
  • 后端域名出现了 5 种写法:有走 Vite 代理的 '/api/',有硬编码的 const API_BASE_URL = 'https://api.example.com',还有直接把全域名写死在组件里的 fetch('http://cdn.example.com/api/v1/...');
  • 唯一的 src/api/api.js 里躺着一个 getUserInfo,而它在 main.ts 里的唯一一次引用是被注释掉的 —— 等于没有;
  • 底层 request.js 里还堆着死代码:timeout: 6000000(约 100 分钟,等于没超时)、被注释掉的 ElMessage.error 导致非 401/403 的错误静默失败、算完却没被使用的三个正则……

一句话总结:工具装了不用,规则写了不接,请求散落一地。

第一个共识:拦截器必须启用

这一步没什么好吵的。反复手写请求头、错误码各写各的,肯定不行;axios 装了却不用,也不行。所以很快达成一致:请求 / 响应拦截器都要接上,header 和错误码统一收口。

真正的分歧,出现在下一个问题上。

分歧:要不要再封一层 api/ 函数?

团队 Leader 的观点很明确:

URL 散落在每个页面里,问题其实不大 —— 因为接口是不会改的。而且每个页面要传的请求参数本来就不一样,这部分你在哪都得重写。header 和错误码统一我同意,但把 URL 单独封装成函数,没必要。

说实话,我当时愣了一下。

因为他这句话是带前提的:“URL 不改”。而”把请求封装成 api/ 层”这件事,在前端早就是约定俗成 —— 大家都这么写,脚手架也这么给。可我还真没细想过:如果 URL 真的永不改,那这层封装到底还剩下什么价值?

把前提拉回”没有 AI 的年代”

我后来想通一件事:API 封装这套习惯,是在没有 AI、纯手写的年代形成的。所以要判断它今天还值不值,最好的办法是把前提拉回那个年代,重新问一遍:

在 “URL 固定 + 全靠手写” 的时代,为什么会有人发明这层封装?

如果 URL 会改,答案很简单:改一处胜过全站 grep 替换,封装是刚需。但现在前提是”不改”。那么把”改动成本”这条理由拿掉之后,剩下的理由还站得住吗?

我把它们一条条摆出来了。

正方:就算 URL 永不改,这层也值

1. 语义 vs 拼接

URL 本身是没有语义的。你自己写熟了,背得下每个路径是干嘛的;但接手的人不知道 /document/libraries/?type=3 到底是查询、分页,还是详情。他每看到一个都得去查一下。

而一个 getLibraryList() / getLibraryDetail(),名字自己就说清楚了。

2. 你在浪费现代编辑器的全部能力

不封装,就意味着现代编辑器为你准备的功能你一个都用不上:JSDoc 注释、参数提示、返回值类型 —— 全看不到。

封装之后这些全回来了:

上了 TypeScript 收益更大:

你直接在页面里写 axios.get('/user/info'),编辑器是无法预知后端会返回什么字段的。而”翻接口文档”这件事,体验永远比”直接看函数签名”痛苦得多 —— 开文档、抄参数、抄响应、关文档,每个接口都来一遍。封装之后,写业务代码时根本不用打开接口文档,一切都在 IDE 里。

3. 认知隔离

写组件的时候,我不想看网络请求。我不想在一堆渲染逻辑里再塞一串 URL 来增加认知负担。哪怕你再熟,眼睛扫到一条裸 URL 也要愣一下去解析它;而扫到一个语义化的函数名 + 注释,观感和心智负担完全不是一个量级。

业务代码和请求细节纠缠在一起,就是最典型的认知污染。

4. 项目一大,封装层就是”活字典”

项目里接口一多(几十上百个),api/ 目录本身就变成前端的一本活字典。

新人想知道”有没有获取列表的接口”,他不用翻几十个页面组件,也不用去翻 Swagger,直接打开 api/goods.js 一眼就看到了。同时它天然避免了不同的人在不同页面重复写同一条请求路径造成的冗余。

5. 复用原则

程序员最基本的方法论就是复用:一个东西只要被调用超过两次,就该抽成一个统一的实现,而不是在每个页面里各改各的。这不是洁癖,这是工程。

一个更关键的点:拦截器和封装,根本不是一回事

反方最核心的一句潜台词是:”拦截器我都接上了,它无所不能,那封装不就是多此一举的套壳?”

但拦截器和封装,解决的是两个维度的问题:

  • 拦截器是”宏观”的:处理所有请求的共性 —— 统一带 token、统一报错弹窗、Loading 开关、401 跳登录、把 response.data 大包裹拆一层。
  • 封装是”微观”的:处理单个接口的个性。

举个具体例子:某个上传头像的接口要传 FormData,而其余接口都是 JSON。如果硬塞进拦截器,你就得写一堆 if (url === '/upload') { ... } 的面条代码,拦截器很快就臃肿到没法维护;而封装成 api/ 里的一个函数,在那一个函数里处理掉就行,干净利落。

换句话说,拦截器只能剥到 code / message 这一层壳。再往下 —— 按接口做类型推导、空数据兜底、业务错误码分流、接口级的缓存 / 重试 / 去重、以及上面那种特例处理 —— 拦截器都做不了,得靠封装层或额外机制。

所以”用 axios 但不封装”,本质上是用了工具的 20%,把剩下 80% 的能力扔了。

插一句:axios 官方到底推荐到哪为止?

争到这里,自然会有人想搬”axios 官方”出来当裁判。但如果真去翻官方文档,会发现一个很有意思的事:它推荐的边界,恰好落在这场争论的外面。

axios 官方(axios-http.com)真正给出”推荐写法”的,就三样地基:

  1. 用 axios.create() 建实例,而不是直接用全局 axios。 把 baseURL、timeout、headers 放进实例配置,不同可靠性的后端用不同实例(实时服务给紧超时,批处理给宽松超时),挂在实例上的拦截器只对该实例生效,关注点自然隔离。
  2. 拦截器处理共性逻辑。 官方列的标准用例就是鉴权、自动刷新 token、日志、Loading、统一错误处理 —— 也就是我们前面”启用拦截器”那步。
  3. 官方文档里确实有一页 Best practices,但讲的还是”实例 + 拦截器 + 配置”这套底座,没再往上规定别的。

注意:axios 官方从头到尾没有推荐过”把请求封装成 api/ 服务层”这种写法。 getUserInfo()、api/goods.js 那一层 —— 具名函数、集中成字典 —— 是社区和框架脚手架的约定,被大量第三方最佳实践文章推崇(抽成 service layer,好处是集中管理、复用、改接口只改一处),但它不属于 axios 自己的官方指引。axios 只负责给你一个配好的实例和拦截器,至于调用侧怎么组织,它不管,也不站队。

于是这场争论有个挺妙的落点:双方谁都搬不出”axios 官方说要 / 不要”当尚方宝剑。 因为官方推荐的范围(实例 + 拦截器)我们本来就已经达成一致了,而分歧的那一层,恰恰是 axios 官方刻意留白、交给团队自己判断的地方。这也正好说明:它只能靠工程权衡去吵,而没有一个”标准”能一锤定音。

反方:在他的前提下,他是对的

写到这里得公平地说一句:**Leader 的判断,在他自己设定的前提下,是完全成立的。**他有几个点确实合理:

  • 对着接口文档写请求,是最自然的开发路径,尤其单点调用、只用一次的接口,直接写反而更直接;
  • 参数确实抽不进 api/。封装解决的从来不是”参数散落”,而是 “URL + method + header 散落”。每个页面的业务参数本来就该、也只能写在页面里 —— 这点他没说错;
  • URL + method 本身带一点语义,GET /user/list 连起来确实能看出个大概。

而封装的全部收益 —— 改一处胜过改 N 处、集中管理、版本演进(/v1/ → /v2/)一处搞定 —— 都建立在”未来会改”之上。一旦锚死”URL 不动 / method 不动 / header 不动”这三个强假设,这些收益就同时归零。

诚实的结论

所以这件事没有非黑即白的答案,判断维度其实很清楚:

  1. 接口到底会不会变? 这是决定性的一条。真能保证三者永不动,不抽是合理的;只要有一条可能变,天平就立刻倒向封装。
  2. 团队多大、有没有新人接手? 单人一次性脚本,封装是负担;多人协作、有人接盘,封装是活字典。
  3. 上不上 TypeScript? 上了,类型提示这条收益直接翻倍。
  4. 同一个接口被调用几次? 大于两次,复用原则就该生效。

封装的价值从来不是”加了什么新功能”,而是”把分散的东西集中起来”、以及”重复 N 次时改动和认知的成本”。 它省的是人的脑子和协作摩擦,不是机器的算力。

一句我一直认的话:规范不是仪式感,但不做工程、只在每个页面里复制粘贴,那就只是在搬砖。 至于”度”—— 用多少、抽多细 —— 那要看具体场景,前提是你心里清楚完整的规范长什么样,再决定在哪儿用力、在哪儿省力。

这次实际怎么落地

回到这个具体项目。既然当下的强假设是”URL 不动”,最终方案是先做基础设施合规,暂不抽 api/:

必做(约 1 人天):

  • 12 处原生 fetch → 统一替换成走拦截器的 apiClient({ url, method, data, params });
  • 5 种域名写法收敛到 request.js 单一来源(dev 走 '/api/' 代理,prod 用 import.meta.env 注入);
  • request.js 里的死代码、失效注释、离谱的超时时间一并清理。

暂不做: 不抽 src/api/、不动业务参数的位置、不改现有页面写法。

留一个触发条件: 一旦出现下面任意一种情况 —— 后端调 URL、加版本前缀、加全局 header、或上线换环境 —— “URL 不动”的前提就失效了,那时候这场讨论本身,就是重新把”抽 api/“提上桌的依据。

说到底,这场争论真正有意思的地方,不在于谁赢了,而在于它逼我把一个”大家都这么写”的习惯拆开,回到它被发明的那个前提去重新审视一遍。很多约定俗成的东西,值得偶尔这样问一句:如果当初的前提变了,你还成立吗?

实习快结束了，我准备再投一些岗位，也想把自己的项目补得完整一点，练习单元测试和 CI/CD。 最开始的问题是：“现在前端一般用什么 CI/CD 工具？”但我并非从零开始。我已经在自己的服务器上搭过 Gitea，也实践过 Docker Compose 管理 Runner。实习所在的团队，则使用阿里云云效。 聊到后面，我发现自己最不舒服的地方，不是流水线写不出来，而是应用的配置、状态和管理入口太分散。一个 CI/CD 选型问题，最后变成了一个应用管理问题。 先分清代码托管、流水线和 Runner这些东西经常一起出现，但它们解决的问题不同。 代码托管负责仓库、权限和协作。流水线负责定义触发条件、任务和依赖。Runner 才是执行任务的环境：拉代码、装依赖、跑测试、构建产物，必要时再执行部署。 GitHub Actions 的官方说明也按工作流、事件、任务、步骤和 Runner 拆解这些概念。Understanding GitHub Actions 因此，前端没有一种必须使用的 CI/CD 工具。比较实际的起点，是看仓库在哪里，以及自己愿意维护多少...
