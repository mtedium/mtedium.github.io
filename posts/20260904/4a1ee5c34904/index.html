基于 DocBook 做网页编辑器，到底该维护 XML、HTML 还是 JSON

发表于2026-09-05|更新于2026-10-15|问题记录
|浏览量:

我们做过一个基于 DocBook 的网页文档项目，可以把目标理解成“网页版 Word”。团队后端使用 Python，客户又明确要求不能脱离 DocBook。

但实际项目已经走向以 HTML 为中心，XML 导出也没有做出来。这次我想复盘的，是当初那个很基础、却越讨论越乱的问题：内容存成 XML，前端要实时编辑，到底应该编辑什么？

讨论中出现了 XML、JSON、HTML、XSLT、CSS、Tiptap，以及“Python 要不要调用 Node”。如果每出现一个问题，就换一种说法宣布“这个才是中心”，架构只会越来越难理解。

我后来觉得，需要先把三个问题分开：文档允许表达什么，编辑器靠什么维护状态，最终发布成什么。

DocBook 给的是文档契约

DocBook 是结构化文档的词汇和约束。章节、段落、列表、交叉引用等元素各有语义，也有合法的组合关系。它可以用来撰写、交换和发布文档，不只是一个让排版“整齐”的模板。

例如，下面是一份很小的 DocBook 5 文档：

它描述的是文章、标题、段落和强调。至于标题的字号、正文的行高，需要由发布方案决定。DocBook 自己的指南也把编写、校验和发布区分开来，介绍了不同的样式及出版路径。DocBook：发布文档

如果客户要求能得到符合 DocBook 规范的文档，这就是系统必须满足的契约。内部改用 JSON，并不能让这项约束消失。

实时编辑需要模型，但模型不等于 JSON 文件

编辑器需要描述内容、选区和修改操作。模型可以是树，可以围绕 XML 设计，也可以提供 JSON 序列化接口。JSON 是一种数据表示方式，不是现代编辑器唯一允许使用的内部结构。

以 Tiptap 为例，它基于 ProseMirror。编辑时维护的是 ProseMirror 的文档节点和编辑状态；getJSON() 得到的是文档的一种可序列化表示。选区、插件状态等不等于都被这份内容 JSON 完整保存了。

输入会引起事务，事务产生新状态，视图再更新对应的 DOM。浏览器已经改动 DOM 的场景，编辑器也可能读取变化并将其转换为事务。不能简单理解成“每按一次键，调用 generateHTML()，再覆盖整个 innerHTML”。ProseMirror Guide

renderHTML 用来声明节点、标记如何表达为 HTML；generateHTML 或静态渲染器负责生成可展示的结果。这和活跃编辑视图处理光标、输入法、撤销重做的过程，有不同的职责。

因此，使用 Tiptap 时，我会优先考虑保存它的结构化文档，而不是反复把 HTML 解析回来。Tiptap 官方同样推荐 JSON 持久化，但也明确支持保存 HTML；这是取舍，不是“保存 HTML 一定失败”的定律。Tiptap Persistence

协同编辑还需要另外设计同步状态、并发合并和持久化方式。选择 JSON 本身不会自动带来协同能力，也不能据此推断某个产品内部一定使用 OT 或 CRDT。

三种“中心”可以同时成立

把问题拆开，原来那些看似矛盾的回答就容易归位了：

关心的问题 作为依据的东西 要保证什么
文档有哪些语义、允许哪些结构 业务需求和选定的 DocBook 版本、子集 内容能表达，导出合法
用户正在编辑哪一份内容 编辑模型及其持久化版本 修改有依据，历史可追踪
发布后长什么样 指定的转换规则、HTML 结构和 CSS 输出符合约定的视觉和功能要求

假设我们选择用 Tiptap 文档 JSON 保存内容，那么它可以是内容的权威存储。与此同时，它的 schema 仍然要容纳客户要求的 DocBook 语义。发布样式也有自己的约束。

这并不需要把 XML、JSON 或 HTML 中的一种宣布为“整个系统唯一重要的东西”。真正要避免的是同一份内容有两份都可以独立修改、却没有同步规则的权威数据。

复用 CSS，也有结构成本

我当时一直纠结样式，是因为项目使用了 DocBook 工具链提供的样式资源。前端如果想直接复用这些 CSS，生成的 HTML 就需要满足相应的选择器和结构约定。

例如，CSS 期望匹配 .section > .title，前端只输出一个没有这些类名的 <h2>，即使语义相近，也不会自然得到相同效果。目录、编号、脚注和交叉引用还可能依赖转换阶段生成的结构。

所以，“借用一份 CSS”和“复制整个发布结果”是两种工作量。

比较实际的选择是，编辑视图只复用能够兼容的样式，必要时加适配层；正式预览则运行真正的发布链。若要求编辑界面与发布界面高度一致，就把结构、类名、编号和样式版本都列入兼容性检查，不能只说“引入 SCSS 就行”。

以 xslTNG 为例，它使用 XSLT 3.0 将 DocBook 转换为 HTML5，并附带网页展示用 CSS，也支持配合分页 CSS 处理器生成打印输出。这些是某套工具链的能力，不代表所有 DocBook 方案都具有完全相同的结构和样式。DocBook xslTNG

XSLT、CSS 和格式化引擎分别做什么

这些名称也曾把讨论带偏。

XSLT 是转换语言，执行它的是 XSLT 处理器。规则文件经常使用 .xsl 扩展名，规范也确实称它为 stylesheet。这个称呼有其正式定义，不必为了和 CSS 区分就说“叫样式表是错的”。W3C XSLT 1.0

XSLT 可以把 DocBook 生成 HTML、另一个 XML 结构或者文本。它也可以在结果中生成类名、内联样式、CSS 内容或 XSL-FO 格式化属性。因此，“XSLT 只换标签，绝不涉及样式”也过于绝对。

生成 HTML 后，浏览器通常通过 CSS 完成视觉呈现。生成 XSL-FO 后，还要交给相应的格式化引擎，才能得到 PDF。转换规则和最终排版引擎是两个角色，不能把“能输出 FO”直接写成“这段 XSLT 就能生成完整 PDF”。

此外，浏览器并非只认识 HTML，XML 也能关联样式表。XML 没有一套普遍适用的默认视觉语义，不等于它不能被展示。W3C：为 XML 关联样式表

对 Python 团队来说，还必须核对处理器版本：lxml 基于 libxslt 提供 XSLT 1.0 能力，不能拿它直接执行要求 XSLT 3.0 的 xslTNG。lxml：XPath 和 XSLT

如果选择结构化文档作为保存格式，HTML 导出可以有两条路线：

路线 A 适合把前端定义的文档表达复用到展示场景，减少另一份手写 HTML 生成逻辑。路线 B 适合正式输出需要遵循既有 DocBook 发布规则的场景。

没有“后端导出 HTML 必须经过 XML”的通用规定。反过来，也没有“前端渲染过，后端就绝不能再生成 HTML”的规定。同一套规则执行两次，和维护两套独立规则，是两回事。

两条路线如果都提供给用户，需要说明各自的用途。不能因为它们都叫 HTML 导出，就默认目录、链接、编号和分页一定一致。

Python 可以调用 Node，复用的是规则

Python 后端无法直接导入一个 JavaScript 包，但可以调用 Node 工具执行渲染。Tiptap 的静态渲染器能在不创建编辑器实例的情况下生成内容，不需要为了这件事启动一个完整的无头浏览器。

需要注意，静态渲染不会自动执行所有编辑器生命周期和事务钩子，自定义 NodeView 也不能假定原样出现在导出结果中。共享扩展时，应把可序列化规则和依赖编辑界面的交互代码分开。Tiptap Static Renderer

我认可多语言工具调用作为一种选择，但不再把它描述成“零维护成本”。判断依据应当是复用规则节省的成本，是否超过增加运行时和部署流程的成本。

真正的大工作量，是覆盖和验证

最初看起来，JSON 转 XML 无非是遍历一棵树。可真正做起来，工作量往往在语义和边界上。

一个平铺的 heading 节点，不一定能直接变成一个完整章节；一个看起来像代码的等宽文本，也未必能区分行内代码、程序清单和命令。图片引用、命名空间、ID、表格和脚注都需要明确映射。

我会先建立一个支持范围，而不是上来承诺完整覆盖标准：

内容 首先要确定的问题
标题、段落、章节 层级怎样组织，哪些位置允许出现
强调、链接、行内代码 属性怎样保留，链接协议怎样限制
列表和表格 合法嵌套是什么，使用哪种表格模型
图片和交叉引用 资源怎样打包，ID 与引用怎样保持一致
不支持的节点 拒绝、只读保留还是明确降级

最有价值的验证是选一份真实的小文档，跑通“导入 → 编辑 → 保存 → 导出 → 校验 → 再导入”，检查语义是否保留。合法 XML 不等于合法 DocBook，合法 DocBook 也不等于没有丢失业务信息。

如果接受外部 XML，还要明确实体、外部资源和转换器文件访问的限制；生成 XML 用结构化 API 处理文本与属性，不能靠字符串拼接碰运气。

回到已经存在的项目

现项目以 HTML 为中心、暂不支持 XML 导出，这是这次复盘的起点。上面的 JSON 模型和 Node 工具，是我重新梳理后的可选方案，尚不能当作已经完成的改造。

我也不能仅凭保存了 HTML，就断定系统没有恢复余地。受约束的 HTML、业务属性和明确的 schema，同样可能保留足够的语义。能否迁移，要拿实际历史数据和客户要求逐项检查；丢失的信息则需要补录，换个编辑器不会自动补回来。

如果再做一次，我会更早要求团队拿出一份文档，证明它编辑之后仍能导出客户接受的 DocBook。编辑体验可以逐步完善，数据契约必须从一开始就能被验证。

实习快结束了，我准备再投一些岗位，也想把自己的项目补得完整一点，练习单元测试和 CI/CD。 最开始的问题是：“现在前端一般用什么 CI/CD 工具？”但我并非从零开始。我已经在自己的服务器上搭过 Gitea，也实践过 Docker Compose 管理 Runner。实习所在的团队，则使用阿里云云效。 聊到后面，我发现自己最不舒服的地方，不是流水线写不出来，而是应用的配置、状态和管理入口太分散。一个 CI/CD 选型问题，最后变成了一个应用管理问题。 先分清代码托管、流水线和 Runner这些东西经常一起出现，但它们解决的问题不同。 代码托管负责仓库、权限和协作。流水线负责定义触发条件、任务和依赖。Runner 才是执行任务的环境：拉代码、装依赖、跑测试、构建产物，必要时再执行部署。 GitHub Actions 的官方说明也按工作流、事件、任务、步骤和 Runner 拆解这些概念。Understanding GitHub Actions 因此，前端没有一种必须使用的 CI/CD 工具。比较实际的起点，是看仓库在哪里，以及自己愿意维护多少...
