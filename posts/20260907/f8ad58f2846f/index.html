前端 CI-CD 选型之后，我更在意应用怎么管理

发表于2026-09-08|更新于2026-10-15|问题记录
|浏览量:

实习快结束了，我准备再投一些岗位，也想把自己的项目补得完整一点，练习单元测试和 CI/CD。

最开始的问题是：“现在前端一般用什么 CI/CD 工具？”但我并非从零开始。我已经在自己的服务器上搭过 Gitea，也实践过 Docker Compose 管理 Runner。实习所在的团队，则使用阿里云云效。

聊到后面，我发现自己最不舒服的地方，不是流水线写不出来，而是应用的配置、状态和管理入口太分散。一个 CI/CD 选型问题，最后变成了一个应用管理问题。

先分清代码托管、流水线和 Runner

这些东西经常一起出现，但它们解决的问题不同。

代码托管负责仓库、权限和协作。流水线负责定义触发条件、任务和依赖。Runner 才是执行任务的环境：拉代码、装依赖、跑测试、构建产物，必要时再执行部署。

GitHub Actions 的官方说明也按工作流、事件、任务、步骤和 Runner 拆解这些概念。Understanding GitHub Actions

因此，前端没有一种必须使用的 CI/CD 工具。比较实际的起点，是看仓库在哪里，以及自己愿意维护多少基础设施：

已有环境 可以先评估的方案 主要要确认的事
GitHub 仓库 GitHub Actions 执行环境、额度和部署网络
GitLab 仓库 GitLab CI/CD Runner 配置、任务规则和产物传递
自托管 Gitea Gitea Actions Runner 运维和工作流兼容性
公司已有云效等平台 沿用现有流水线 权限、环境和发布流程的约定

GitLab 使用 .gitlab-ci.yml 配置任务，也由 Runner 执行，但配置语法和 Actions 工作流并不相同。能迁移的是对触发、依赖、产物和失败处理的理解，不能把 YAML 改个文件名就当成迁移完成。GitLab CI/CD

至于“某家大厂到底用什么”，公开案例可以提供参考，却不能代表所有团队、所有时期的实际部署。我更愿意先把自己的交付流程讲清楚。

Gitea 轻，不代表构建也轻

我当时选择 Gitea，一个很直接的原因就是服务器配置不高。代码托管服务的资源需求和前端构建任务的资源需求，需要分开估算。

一个能轻松运行 Git 服务的机器，不一定能同时承受多个依赖安装、测试和打包任务。Runner 放在哪里，是下一步单独要决定的事。

GitHub Actions 可以构建后通过 SSH 等方式部署到自己的服务器；也可以使用自托管 Runner，在能访问目标环境的机器上执行任务。自托管并不要求 Runner 与生产应用在同一台机器，维护、更新和运行环境则由自己负责。GitHub：自托管 Runner

所以，“服务器低配，就应该把构建也放在本机”并不成立。远端构建能减少生产服务器的 CPU、内存压力，本机构建可能减少产物传输，但也会争抢应用资源。该选哪种，要看实际瓶颈是计算、带宽，还是网络可达性。

我没有测量过完整部署耗时，不能直接把某种方案写成“快很多”。

单测要覆盖项目真正容易出错的规则，比如表单校验、状态变化或复杂数据转换，而不是为了让流水线多一个绿色步骤。

我更关心这些结果能否观察到：故意制造一个失败用例时，部署是否停止；修复后，部署的产物能否对应到那次提交；发布失败后，能否回到上一份产物。

CI 失败也不会自动禁止合并。想形成合并门禁，还要在仓库里配置分支保护和必需检查。部署任务如果是另一个 job，则必须设置清楚它与检查任务的依赖，不能只写“main 分支时运行”就默认它一定等测试通过。

部署凭证只交给需要它的受信任任务。自托管 Runner 会执行仓库代码，也不宜为了省事就让外部贡献的任务获得生产环境权限。

Gitea Actions 兼容 Actions，但要核对版本

Gitea Actions 以兼容 GitHub Actions 为目标，这能降低工作流学习成本。不过，兼容不是完全等价。Gitea 官方文档单独列出了不支持的语法、缺失功能和行为差异。Gitea：与 GitHub Actions 的差异

实操时需要对照部署版本，检查 action 下载来源、上下文、Runner 标签以及工作流功能。不要看到教程里的 runs-on: self-hosted 就照抄：任务能否被领取，取决于 Runner 实际注册的标签和对应执行方式。

同样，工作流跑在 job 容器里时，里面的目录和宿主机目录并不是一回事。简单执行 cp dist/* 某个路径，不代表文件已经进入生产服务的目录，更不能默认完成了一次可回滚发布。

Compose 为什么仍然让我觉得麻烦

我已经用过 Compose，困扰也正是在这里出现的：启动方式写在 Compose 里，Runner 的一些行为仍需要生成、挂载和修改配置文件。过一阵子再回来，还得重新确认它们的关系。

这里至少有三类信息：

信息 作用
Compose 定义 镜像、网络、挂载、环境变量和重启策略
Runner 运行配置 并发、工作目录、缓存等运行行为
注册后的身份数据 Runner 与 Gitea 的连接身份和注册状态

以 act_runner 为例，官方文档分别说明了配置生成、注册和 daemon 运行。注册生成的 .runner 文件也需要妥善保留；把注册地址和 token 随意塞进运行配置，并不能替代注册流程。Gitea Act Runner

这几类信息有不同生命周期。普通配置可以版本管理，真实 token 和注册身份数据不应该一起提交。

我的诉求其实可以表述为：我希望所有管理动作有一个可发现的入口，而不是靠记忆维持这些关系。 这个入口可以生成工具需要的配置，不必要求每个工具原生支持完全相同的配置形式。

容器也有边界：如果挂载宿主机 Docker socket，Runner 便能够控制宿主机 Docker。它不会因为自己在一个容器里，就自动拥有完整的安全隔离。

包管理和进程管理，是两个层次

讨论时我把 sysctl 和 systemctl 混在一起过，这里需要纠正。sysctl 用来配置运行中的内核参数；管理 systemd 服务常用的是 systemctl。Linux 内核：sysctl

我更喜欢把后来安装的应用集中管理，与系统自带组件区分开，所以会在意 Homebrew 这样的入口。

但 Homebrew 在一个前缀下管理软件，不等于容器或虚拟机提供的运行隔离。Linux 上的 brew services 底层也使用 systemctl，默认用户服务与使用 sudo 时的系统服务有区别。它提供的是更统一的管理界面，并没有消灭底层服务管理器。Homebrew Manpage：services

类似地，Compose 的重启策略依赖 Docker daemon 正常运行，也不是脱离操作系统就能自我管理。

这让我重新理解“干净”：对我而言，更重要的是软件和数据的位置可追踪、安装与启动可重建、退出和升级有边界。至于底层是否使用 systemd，可以另外判断。

我想做的，可能是应用管理器

后来我给这个需求起了一个更准确的名字：应用管理器。

它先不用重新实现包管理器、容器引擎和进程守护。我想解决的是：

  • 能从一个入口看到自己管理了哪些应用。
  • 能找到每个应用的启动定义、配置、数据和日志。
  • 能区分可重建的声明、需要备份的数据和需要单独保管的凭证。
  • 能用同一种操作方式调用已有的运行工具。

这还是项目设想，不是我已经完成的系统。声明式配置、用户级服务、配置管理工具等路线也值得评估；没有必要为了一个统一入口就先发明一套新的基础设施。

我尤其不会再把“把文件夹拷过去就能迁移”当成当然结论。架构、动态库、端口、权限、数据库状态和外部资源，都会影响能否恢复。

同样，一个只靠 nohup、PID 文件和 kill 的脚本可以帮助验证界面想法，但离稳定的应用管理还有距离：PID 可能复用，子进程可能没退出，崩溃和机器重启之后又该怎么办，都需要回答。

这次讨论让我明确了两件可以分别推进的事：先用已有平台把项目检查和发布跑通，再用应用管理器的设想解决我自己的维护负担。等真正做过、测过，再把结果写进项目经历。
