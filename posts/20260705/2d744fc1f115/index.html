前端什么时候该用 class？从一次 OOP 讨论说起

在前端写久了，很容易遇到一个疑问：学习编程时反复强调封装、继承、多态，真正写 React 项目时，却大多在写函数、Hook 和数据转换。偶尔出现几个 class，往往还是 SDK 或连接管理相关的代码。

于是问题来了：是前端没有用好面向对象，还是面向对象本来就不该成为默认答案？

一次关于 OOP 的讨论，让我开始换一种问法：这段代码有什么东西需要被保护，又有什么复杂度需要被藏起来？

比起争论哪种范式更先进，这个问题更容易帮助我们决定，眼前到底需不需要一个 class。

先把 class 和 OOP 分开

class 是一种语言机制，面向对象是一种组织程序的思路。写了 class，不代表就做好了封装；没有 class，也不代表无法组织对象和行为。

比如，把十几个公开字段放进一个类，再配上一组可以任意修改它们的 setter，形式上有了对象，调用方却仍然要理解所有字段之间的关系。复杂度并没有消失，只是换了个容器。

反过来，一个模块通过闭包保存内部状态，只暴露少量操作，也可以形成很清楚的封装边界。

所以，我更关心的不是有没有 class 关键字，而是：调用方能不能少知道一些内部细节，同时不容易把事情做错。

封装的价值，在于守住规则

以一个不允许透支的账户模型为例，它需要守住“余额不能小于零”这条规则。

如果余额可以被任意赋值，那么每个调用方都必须记住检查它。页面记住了，批量导入可能忘了；正常流程检查了，异常恢复路径可能漏了。规则散落在多个地方，维护就会越来越依赖人的记忆。

如果余额只能通过存入、支出这些操作改变，检查就可以收进同一个边界。外部只需要表达“我要支出多少”，不必自己计算余额、检查是否合法，再把结果写回去。

这就是不变式的意义：不管经历了什么合法操作，某些条件始终成立。

class 很适合表达这类边界，但私有字段只是工具。真正决定封装是否有效的，是每条修改路径有没有遵守规则，以及有没有把可变的内部数据直接交给外部。

还要注意 TypeScript 的一个细节：private 主要在类型检查阶段限制访问，JavaScript 的 # 私有字段则提供运行时的访问限制。二者不能完全等同。具体区别可以看 TypeScript 的类文档。

多态也不一定需要继承树

另一个常见误解是，想获得多态，就得先建一个抽象基类，再让所有实现继承它。

例如，调用方需要发送消息，可以依赖一个约定好的发送接口。至于背后走 HTTP、WebSocket，还是测试时使用的替身，只要满足约定，调用方就不必知道具体实现。

在 TypeScript 中，这个实现既可以是类实例，也可以是一个带有方法的普通对象。它的类型兼容性主要基于结构，而不是要求所有实现都有同一个父类。相关规则见 TypeScript 类型兼容性文档。

因此，设计接口和设计继承关系是两件事。我们可以先定义调用方真正需要的能力，再判断实现是否需要 class。

另一类问题则适合用判别联合：例如一组已经明确的动作，包括拍照、开始录像、停止录像，每种动作携带不同参数。通过共同的类型标记，处理函数可以区分它们，并进行穷尽检查。这个机制可以参考 TypeScript 的类型收窄文档。

两种组织方式的扩展方向不同：如果希望外部持续增加实现，而调用方保持稳定，接口会比较自然；如果变化主要来自一组明确的数据分支，并且希望集中检查是否处理完整，判别联合会比较直接。

不必把它们排出高下，先看变化会从哪里发生。

为什么写 React 时，函数往往更顺手

很多前端工作都沿着一条很直观的路径展开：拿到数据，做转换，根据当前状态描述界面，再响应用户操作。

对这样的逻辑，函数通常已经足够。格式化时间、筛选列表、计算展示字段，本身没有需要长期持有的资源，也不一定有必须隐藏的可变状态。把它们包装成类，可能只是多了一个构造步骤。

React 的函数组件和 Hook，也让我们更习惯通过组合来组织 UI 和复用逻辑。

但这不意味着函数组件没有身份或生命周期。组件函数会在渲染时再次执行，而 React 会根据组件在渲染树中的位置、类型以及 key 等信息决定状态的保留与重置。**一次函数调用结束，不等于对应组件的状态就消失了。**这点在 React 关于保留和重置状态的文档中有详细说明。

这里真正影响代码组织的，是我们通常不需要自己创建一个组件对象，再不断命令它修改界面。我们描述当前状态对应的 UI，让 React 负责后续更新。

所以，我会优先把纯粹的数据转换写成函数，把依赖 React 状态和 Effect 的复用逻辑放进 Hook；遇到独立于 UI、需要管理状态和资源的部分，再考虑对象。

class 容易发挥价值的地方：资源的归属

相比“用户”“订单”这些名词，连接、播放器、订阅这样的资源，常常更能让我看清一个对象的必要性。

以 WebSocket 连接为例，调用方可能只想发送和接收消息，实现内部却要处理连接状态、事件监听、重连定时器和关闭后的清理。如果这些东西分散在页面里，页面就得同时承担界面展示和连接管理两种职责。

这时，一个连接对象可以把相关资源收在一起，对外只暴露少量操作。它的价值不是让代码看起来更“面向对象”，而是明确回答几个问题：

  • 谁拥有这个连接？
  • 谁负责移除监听器、取消定时器？
  • 关闭以后，还允许执行哪些操作？
  • 重复关闭会发生什么？

class 可以把这些约定集中表达出来，返回操作方法的工厂函数也可以。最终要看哪一种更容易读懂，更容易保证资源被正确释放。

即使用了 class，生命周期管理也不会自动正确。对象由谁创建、何时销毁，仍然需要设计清楚；如果它被 React 组件使用，还需要让资源的获取和释放与相应的 Effect 生命周期配合。

我的判断顺序

现在遇到“这里要不要写 class”，我会先看三个问题。

**第一，这段逻辑主要是在转换数据，还是在管理一个持续存在的东西？**前者通常从函数开始就够了；后者值得进一步考虑对象边界。

**第二，状态之间有没有必须共同维护的规则？**如果几个字段不能各改各的，把修改入口集中起来，往往比单纯统一类型更有价值。

**第三，封装之后，调用方是否真的轻松了？**如果外部仍然需要按复杂顺序调用十几个方法，知道内部每个阶段才能用对，那么即使已经写成类，也还没完成好的封装。

不必要求所有条件同时成立，更不必给前后端各划一个固定比例。同一个项目里，函数、模块、普通对象和 class 完全可以各司其职。

这次讨论给我的收获，是把注意力从范式的名头移回了代码的责任：普通转换交给函数，需要共同守护的状态收进边界，需要释放的资源明确归属。

当一个 class 让调用方少操心了一整组规则和细节，它就有了存在的理由。
