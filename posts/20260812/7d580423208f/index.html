Gitea 推送遇到 HTTP 413：先查请求链路，再分清 SSH 端口

|浏览量:

向自己的 Gitea 推送代码时，日志出现了：

最后一句很容易让人误以为已经推上去了。但前面明确发生了失败，不能只挑一句好看的输出判断结果。

我的访问路径里还有 Cloudflare，服务器没有公网 IP，但可以通过虚拟局域网连接。这几个前提决定了：需要先确认请求经过哪些节点，再选择能实际到达 Gitea 的路线。

413 表示请求体太大，不直接说明是哪一层拒绝

HTTP 413 表示接收方认为请求体超过可接受范围。对 git push 来说，拒绝可能来自 Cloudflare、反向代理或 Git 服务入口。不能仅凭状态码就锁定 Nginx，也不能断定某一个文件一定超过某个数值。

先记录完整远程地址、push 退出状态和大致传输量，再检查代理与服务日志。Cloudflare 的 413 官方说明列出了与套餐及站点配置有关的上传限制。具体额度应查当前设置，不宜把某个免费套餐数字推广成所有部署的限制。

http.postBuffer 也不是服务端上传配额。Git 官方配置说明指出，提高它主要影响是否使用分块传输，通常不是多数推送问题的有效解决方案，还可能增加内存占用。它不会解除 Cloudflare 或反向代理的请求体限制。

没有公网 IP，关闭代理不一定能直连

如果域名通过 Tunnel 才能访问源站，把 DNS 切成直连并不会凭空创造一条到源站的公网线路。

这里有三个独立概念：服务器主机指纹用于确认连到谁；SSH 公钥用于证明你是谁；Gitea 仓库权限决定你能读写什么。提交邮箱、网站登录密码和系统用户密码不能混为一谈。

对外展示端口与容器监听端口要分别看

Gitea 的 SSH_PORT 用于生成展示给用户的克隆地址；SSH_LISTEN_PORT 影响内置 SSH 服务的监听，不能一看到外部端口是 222 就把容器内部也改成 222。标准 rootful Docker 镜像还涉及镜像内 OpenSSH 与内置 SSH 的选择，应先确认运行方式。

在 222:22 这个例子里，外部克隆入口需要显示 222，容器实际服务仍需监听映射右侧的 22。Gitea Docker 安装文档展示了主机与容器端口分离的部署方式，配置手册解释了 SSH 相关配置项。

仓库体积要处理，但别直接丢历史

直连是解决传输路径问题，仓库瘦身是另一个问题。删除工作区里的大文件、提交 .gitignore，不会让旧提交里的大对象消失；新建 .gitattributes 也不会自动把既有历史全部迁移成 LFS。

Git LFS 可把合适的二进制文件转到独立对象存储，但 LFS 上传仍要经过自己的 HTTP 链路，不能保证绕过同一个代理限制。若要迁移历史，需要另外评估影响、备份并协调使用者。参见 Git LFS 官方项目。

分批推送只有在每一批新增对象都低于限制时才有意义，HEAD~5 表示某个祖先提交，不是“自动拆成五份”。若某次提交本身就携带很大的对象，换一个祖先也不保证可行。不应该为了绕过 413，直接删除 .git 或无解释地强制推送。

最后用提交 ID 验证结果

按实际分支对照两个提交 ID，再查看 Gitea 页面。IDE 关于某个 loose ref 文件不存在的警告，也不能单独证明仓库损坏：引用可能已打包，应让 Git 的引用命令判断，而不是手工改 .git。

这次问题真正需要理清的是：HTTP 走了哪条路、SSH 连到了哪个端口、认证属于哪个系统。明确这些以后，才能判断该改代理、改 remote，还是处理仓库对象体积。
