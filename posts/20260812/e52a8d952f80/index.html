用 Docker Compose 管理 Gitea Runner：先分清镜像、容器和任务

发表于2026-08-13|更新于2026-10-15|问题记录
|浏览量:

Gitea 装好了，仓库也能推送，接下来把工作流放进 .gitea/workflows/，是不是就能自动构建？

我在配置时卡住的第一件事，是不知道 Runner 到底应该放在哪里：和 Gitea 放进同一个镜像，单独运行一个二进制，还是往原来的 Compose 文件再加一段？

把这里理顺以后，很多看起来像“注册失败”的问题，实际上连 Runner 容器都还没创建。

Gitea、Runner 和 Job 分别负责什么

Gitea 保存仓库、接收事件、安排任务；Runner 领取任务并汇报结果；Job 执行工作流中的步骤。使用 Docker 执行模式时，Runner 还会通过 Docker daemon 创建临时的 Job 容器。

所以，同一个 Compose 项目里可以有 Gitea 和 Runner 两个服务，但这不表示它们共用一个镜像，也不表示 Job 就在 Runner 自己的容器里执行。官方的 Runner 概述也区分了 Docker、DinD 和 host 等执行模式。

以下示例针对 Linux Docker Engine、Compose v2 和 gitea/runner 3.x，采用挂载宿主机 Docker socket 的基础镜像；不是旧版 gitea/act_runner 的教程。Gitea 与 Runner 各自独立发布，版本号不能互相套用。

pull 下载的是镜像，Compose 描述的是运行方式

docker pull 不会把软件“安装进当前目录”，也不会自动创建一个可运行的服务。它把镜像交给当前 Docker daemon 管理。

Compose 文件则描述要用哪个镜像、挂载哪个目录、加入哪个网络、用什么环境变量启动。配置文件放在用户目录、/srv 或其他位置，都可以引用同一台 daemon 已经保存的镜像。./runner_data:/data 中的相对路径才和 Compose 文件位置有关。

对象 作用 常见操作
镜像 创建容器的模板 docker image ls、docker image rm
容器 某次运行的实例 docker compose ps、docker compose stop
Compose 文件 声明如何创建服务 docker compose config、docker compose up
挂载目录 保存需要持久化的数据 由 volumes 显式声明

因此，docker rm gitea/runner:3 会找错对象：这看起来是镜像名，删除镜像应使用 docker image rm。如果仍有容器引用它，应先确认容器用途，不能靠强制删除掩盖问题。

下面是增加到已有 Compose 文件中的片段。假设原 Gitea 服务名为 server，它已经加入 gitea 网络。保留原有 server、数据库和卷配置，再合并这个服务，不要用片段覆盖整个文件。

这里用 3 表达 Runner 主版本；需要可重复部署时，应改成自己验证过的精确版本或 digest。实例地址要从 Runner 所在环境验证，例如 https://git.example.com/；不能把容器里的 localhost 当作宿主机。注册令牌从计划使用的仓库、组织或实例级 Runner 设置页获取，只在本地注入，别写进博客或仓库。

基础镜像通过 socket 连接宿主机 daemon，无需额外开 privileged。它也意味着构建任务可能接触宿主机资源，因此该例适合可信仓库，正式环境可把 Runner 和 Gitea 分机器部署。官方 Docker 安装文档说明了镜像、注册变量、持久化和这一权限边界。

默认 /data/.runner 保存注册状态。容器重建时保留 /data，就能继续使用已有身份；删除这个目录不是解决所有连接故障的通用办法。

新增服务要 up，修改环境变量也要重新创建

restart runner 只能重启已有容器，不会创建尚不存在的 Runner，也不会把新改的 Compose 环境变量写进旧容器。修改 Compose 后通常用 up -d runner 应用；修改已挂载文件的内容，则要确认程序是否支持热加载，Runner 配置需要重启后读取。

depends_on 的简单写法保证启动顺序，不保证 Gitea 已经能接受注册请求。启动早期短暂 connection refused 后恢复正常，和一直重启是两种情况。若要等服务就绪，给 Gitea 定义有效健康检查，再使用 condition: service_healthy。Compose 的启动顺序说明解释了这个区别。

排错时优先用 docker compose logs runner，这里的 runner 是服务名。docker logs 接收的是实际容器名或 ID，两套名字不要混着猜。

Runner 在线以后，再确认工作流能否执行

网页上出现 Runner，只能证明注册和连接走通。接下来还要确认仓库开启 Actions、工作流路径正确、runs-on 与 Runner 标签对应，以及 Job 镜像和 Action 能被获取。

runs-on: ubuntu-latest 是调度标签，不是“免费分配一台 GitHub 的 Ubuntu 机器”。它的具体执行环境由自己的 Runner 配置决定。Runner 标签文档给出了标签与 docker://...、host 的对应关系。

Runner 也不只做 CI。步骤可以运行测试、构建镜像、上传产物和部署服务；能否完成 CD，取决于执行环境是否具备到目标机器的权限和部署通道。增加 Jenkins 是另一种平台选择，并不能自动修复当前的镜像、网络或目录问题。

我更愿意把最初的检查收敛成四件事：服务是否创建、进程是否启动、注册是否成功、任务是否真正运行。每一步都有对应证据，比一看到“不在线”就重新生成令牌更容易定位。
