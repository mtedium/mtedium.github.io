Docker 镜像总是拉不下来：从超时、仓库地址到离线搬运

发表于2026-08-13|更新于2026-10-15|问题记录
|浏览量:

配置 Gitea Runner 时，我遇到过一种特别绕的状态：Compose 文件看着没问题，镜像却始终拉不下来。换了镜像站，错误从超时变成 403、429，再变成 pull access denied。后来把镜像从笔记本搬到服务器，容器又报 exec format error。

这些报错发生在不同阶段。把它们都理解成“Docker 源不好用”，就会不断更换配置，却不知道哪条假设已经被验证。

先分清到底在拉哪个镜像

一条流水线可能涉及至少三类镜像：Runner 本身、执行 Job 的环境，以及项目 Dockerfile 的基础镜像。

例如，Runner 使用 gitea/runner:3，Job 使用 docker:27，项目的 Dockerfile 又写了 FROM node:22-alpine。第一个在 Compose 启动时获取，第二个在准备 Job 时获取，第三个在项目构建时获取。

Dockerfile 存在于本地，只说明构建配方在本地，不代表它引用的基础镜像也已经存在。宿主机 docker --version 显示什么版本，也不等于已经有同版本的 docker:<tag> 镜像。

先看日志中完整的 image= 或 failed to pull image，再去检查那个对象：

如果 Runner 连接的是另一台 Docker daemon 或 DinD，当前终端看到的本地镜像库也可能与它不同。

错误信息会告诉你排查哪一层

错误 已经知道什么 接下来检查
lookup ... no such host 名称解析失败 当前 daemon 的 DNS 和实际请求域名
dial tcp ... i/o timeout 连接未在期限内建立 路由、防火墙、代理、目标可达性
403 Forbidden 收到了服务端拒绝 响应来自哪个源、访问政策、权限
429 Too Many Requests 请求被限流 实际 registry、限流规则和认证状态
pull access denied、denied 仓库访问被拒绝 完整仓库路径、权限、标签是否存在
exec format error 已进入运行阶段 CPU 架构、入口文件格式等

连接日志里出现一个意外 IP，并不足以直接证明 DNS 污染；还要对比可信解析结果、代理和本机 DNS 配置。排错的目标是增加证据，不是给每种超时套一个固定原因。

私有仓库不自动等于 Docker Hub 加速器

registry.example.com/team/runner:3 代表一个具体 registry 下的具体仓库。创建了私有镜像实例、登录成功，并不会让它自动代理 docker.io 的全部公共镜像。

同样，给官方镜像前面随意加一个 registry 域名，不能保证那个地址确实托管了该镜像。要么供应商明确提供 Docker Hub 拉取缓存，要么先把镜像推到自己的仓库，再在 Compose 中使用对应的完整名称。

Docker 的 registry mirror 文档说明了拉取缓存的工作方式。第三方服务的配额、访问范围和可用性会变化，不应把一串旧域名当作长期有效的答案，更不能据此推导“国内加速服务全部消失”的历史结论。

终端能走代理，不代表 dockerd 会走

执行 docker pull 时，真正访问 registry 的通常是 Docker daemon。给当前 Shell 导出代理，或者给 Runner 容器设置代理，都不自动等于 daemon 已配置。

离线搬运时，平台、标签和 daemon 都要一致

服务器暂时无法联网时，save / load 是可以理解、可检查的办法。不过从 Apple 芯片笔记本搬到 x86 Linux，不能忽略架构。

Compose 引用 :3，导入的也要有 :3；只有 :latest 不意味着 :3 已存在。使用同一个 daemon，并确认离线启动不会强制重新拉取；Compose v2 可在镜像和依赖都已就绪时使用 docker compose up -d --pull never runner。

镜像归档应用 docker image save 与 docker image load。容器文件系统导出的 export / import 是另一套用途，不能拿来直接替代。

镜像好了，后面仍可能有网络问题

如果下一次失败变成 Unable to clone https://github.com/actions/checkout，说明镜像阶段已经往前走了，接下来失败的是获取 Action 代码。它不是再次拉 Runner 镜像。

把镜像、Action 代码、业务仓库和 npm 依赖四种下载分别识别出来，才知道应该改 daemon、Runner 还是 Job 环境。一次只解决日志明确指向的那一层，配置才不会越堆越难理解。
